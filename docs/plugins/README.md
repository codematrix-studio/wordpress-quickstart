# Собственные плагины

Функциональность, которая не относится к представлению сайта, размещайте в плагинах. Она должна сохраняться при смене темы.

В репозитории есть минимальная заготовка `quickstart-tools`. Она показывает точку входа плагина и не регистрирует демонстрационные сущности автоматически.

## Когда создавать плагин

- Типы записей и таксономии.
- Метаполя и административные настройки.
- Интеграции с внешними сервисами.
- REST API и AJAX-обработчики.
- Прикладная логика, общая для нескольких тем.

## Основные требования

- Проверяйте права пользователя через capabilities.
- Проверяйте nonce там, где он применим; nonce не заменяет проверку прав.
- Валидируйте входные данные и экранируйте вывод.
- Используйте API WordPress вместо прямого доступа к базе данных, когда это возможно.
- Не подключайте обработчики и библиотеки без необходимости.

## Хранение кода в Git

Собственные плагины размещайте непосредственно в `wp-content/plugins/` и добавляйте в Git. Не помещайте собственный код в каталог стороннего плагина.

Git игнорирует стандартные плагины и темы, поставляемые с WordPress, но остальные каталоги `plugins/`, `themes/` и `mu-plugins/` доступны для версионирования. Сторонние компоненты, установленные только для локальной разработки, добавляйте в локальный файл `.git/info/exclude`, чтобы не менять общие правила репозитория.

MU-плагины размещайте в `wp-content/mu-plugins/`. Помните, что WordPress автоматически загружает PHP-файлы непосредственно из этого каталога; для организации кода в подкаталогах используйте отдельный загрузчик верхнего уровня.

Справка: [Plugin Developer Handbook](https://developer.wordpress.org/plugins/).
